## Method assignments: TDD vs SDD (Plans 004–007)

| Plan | Method | Rationale |
|---|---|---|
| 004 | Hybrid | Manifest generator is pure logic → strict TDD; rolldown/package.json are configuration → verification gates. |
| 005 | Strict TDD | The install transaction's guarantees (idempotency, integrity, crash recovery, dry-run honesty, conflict keep) are each a test; tests are the executable spec. |
| 006 | Strict TDD | Uninstall/update/doctor safety semantics (report-only without state, hash-based update, exit codes) are behavior contracts best pinned test-first. |
| 007 | Verification-gated checklist | Docs, packaging metadata, and publishing are not test-first material; each step carries a machine-checkable gate instead. |

SDD (full spec/design/task pipeline) was considered and deliberately NOT
used: single-implementer repo, one cohesive feature, and the cross-plan
contracts (manifest schema v1 in Plan 004, state schema v1 in Plan 005, JSON
schema v1 in Plan 006) are embedded as normative sections inside the plans —
the same information a delta spec would carry, without a second artifact
chain to keep in sync. Tests + embedded schemas are the specification of
record. Revisit SDD if the installer grows multiple independent features or
multiple implementers.

## Architecture boundary

- Agent and command Markdown define behavior and native tool permissions.
- Markdown cannot observe lifecycle events or guarantee that a model continues.
- Only Plan 003 adds code, solely to react to `session.idle` and issue one
  guarded continuation prompt when actionable todos remain.
- This project takes behavioral inspiration from oh-my-openagent. It does not
  copy OmO's TypeScript agent factories or depend on its runtime packages.

## Deliberately excluded

- OmO Team Mode and its `team_*` tools
- Hash-anchored editing
- LSP, AST-grep, tmux, and bundled MCP implementations
- Runtime model fallback chains
- Persistent autonomous continuation loops
